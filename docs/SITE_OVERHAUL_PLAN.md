### Yahoo and news data flow

The intended pipeline is:

```text
GitHub Actions schedule/manual run
  -> workflow injects Yahoo secret values as process environment variables
  -> scripts/pull_yahoo.py refreshes a short-lived Yahoo access token
  -> Yahoo Fantasy API returns league, standings, scoreboard, teams, and rosters
  -> script writes raw and simplified JSON under _data/
  -> scripts/pull_news.py writes _data/news.json
  -> workflow commits changed _data/*.json files to main
  -> GitHub Pages rebuilds the Jekyll site
  -> Liquid reads site.data.* and renders index.md
```

The workflow runs on a six-hour cron and supports manual dispatch. It requests `contents: write`, checks out the repository, installs Python 3.11 and `requests`, runs `scripts/pull_yahoo.py`, runs `scripts/pull_news.py`, stages `_data/*.json`, commits, and pushes when the working tree changed.

The inspected paths are internally consistent:

- `.github/workflows/update.yml` calls `scripts/pull_yahoo.py`, which exists.
- It calls `scripts/pull_news.py`, which exists.
- Both scripts write JSON under `_data/`.
- The workflow stages `_data/*.json`, matching those outputs.
- The nested duplicate `scripts/scripts/pull_news.py` is not referenced.

The workflow passes four secret names to `pull_yahoo.py`. The script reads them only from the environment and does not intentionally print them. The authentication architecture must remain unchanged until a separately reviewed migration is approved.

### Current automation and data findings

1. The latest public scheduled runs inspected ended at the `Pull Yahoo data` step with failure. The most recent inspected failure was 2026-06-05. The news and commit steps were skipped after that failure.
2. The repository's latest generated data describes the completed 2025 league, while the supplied live Yahoo URL is the 2026 league. Yahoo league identifiers are season-specific, so the automation target is stale or no longer resolving successfully.
3. The raw Yahoo JSON files are populated, but all simplified outputs currently contain no usable teams or matchups:
   - `standings_simple.json`: empty array
   - `scoreboard_simple.json`: week value plus an empty matchup array
   - `rosters_simple.json`: week value plus an empty team array
4. Yahoo's returned `team` values contain nested list structures. `flatten_team()` merges only immediate dictionaries and does not recursively flatten the nested metadata list. This is the likely reason the normalizers cannot find team names and keys even though the raw files contain 12 teams.
5. The homepage condition treats an empty standings array as present and renders an empty table. The matchup card has a stronger size check and correctly displays a waiting message.
6. `league_meta.json` is rendered wholesale on the public homepage. The public raw responses also contain manager identifiers and league invitation metadata that are not needed by the site. These are not OAuth credentials, but publishing them violates least-exposure design and should be corrected before expanding the data pipeline.
7. All three configured news feeds currently produce visible error messages instead of news. `pull_news.py` converts failures into ticker items, and its changing timestamp can create a commit even when no valid article was retrieved.
8. Python packages and action versions are not captured in a project dependency file. The Actions are pinned to major tags, and `requests` is installed without a version constraint.
9. The workflow has no concurrency guard. Manual and scheduled runs could overlap and compete to push the generated commit.
10. The workflow checks the whole working tree for changes but stages only `_data/*.json`. This is acceptable with the current scripts, but it can fail if a future script changes a non-JSON file without changing a JSON file.

- A stable owner identity owned by this website

## Proposed data architecture

### Design rules

- Use stable lowercase IDs such as `turnbull-acs` as internal foreign keys.
- Keep owner identity separate from franchise identity.
- Store mutable display names and historical aliases explicitly.
- Store Yahoo league/team mappings by season; never join on team name.
- Separate curated historical facts from generated current-season data.
- Store only public, page-required fields in committed generated JSON.
- Keep OAuth credentials and refresh tokens exclusively in GitHub Actions secrets.
- Include `source` and `verified` metadata for manually migrated historical facts.
- Represent unknown facts as `null` or omit them; do not invent values.

### Owners

Recommended file: `_data/owners.yml`

```yaml
- owner_id: owner-example
  display_name: Example
  aliases: []
  active: true
  joined_season: 2021
  departed_season:
```

Do not store email addresses, Yahoo GUIDs, authentication identifiers, or private contact details.

### Records and leaderboards

Recommended file: `_data/records.yml`

```yaml
- record_id: single-game-team-points
  category: single_game
  subject_type: franchise
  label: Most team points in one game
  direction: highest
  entries:
    - rank: 1
      franchise_id:
      owner_id:
      season:
      week:
      value:
      opponent_franchise_id:
      verified: false
```

Use typed record categories rather than one bespoke table per page. Additional categories can represent career records, season records, playoffs, margins, streaks, and bench scoring misses. Bench misses require `player`, `points_missed`, `week`, `season`, and `franchise_id` fields.

Derived records should eventually be generated by a deterministic script from normalized season data. Manually entered legacy records must retain source and verification fields.

### League votes

Recommended file: `_data/votes.yml`, with one file per season if volume grows.

```yaml
polls:
  - poll_id: 2026-week-01-winners
    season: 2026
    week: 1
    type: matchup_winners
    status: scheduled
    opens_at:
    closes_at:
    ballot_url:
    options: []
    results: []
    updated_at:
```

GitHub Pages cannot accept authenticated votes because it is a static host. The site can display polls and committed result snapshots, but ballot collection requires a separate free service such as a commissioner-owned form, or a manual repository workflow. No client-side code should pretend to save authoritative votes locally. Power rankings and picks should follow the same pattern: external/manual input, validated committed output, static rendering.

### Generated current-season data

The current raw/simplified split should become an allowlisted generated schema:

```text
_data/generated/
├── manifest.json
├── league.json
├── standings.json
├── scoreboard.json
└── rosters.json
```

`manifest.json` should include schema version, season, source update time, generated time, and status. Generated files should contain only fields actually used by public pages. Raw Yahoo responses should not be rendered and should not remain permanently committed once sanitized fixtures and normalized output are proven. If raw responses are needed for debugging, store redacted short-retention Action artifacts rather than public site data.

## Risks and technical limitations

### Data and authentication

- Yahoo identifiers change by season; the 2025 stored data and 2026 live league must be mapped explicitly.
- Yahoo API response shapes are deeply nested and can vary by endpoint or season. Tests must use sanitized fixtures and tolerant parsers.
- The current scheduled Action is failing before data generation. The precise credential/API error was not exposed in this audit and must be diagnosed through a controlled manual run by an authorized repository administrator.
- Raw API responses include more metadata than public pages need. Public output must use an allowlist.
- Private military-style league jokes, personal details, and other narrative copy are editorial content, not API facts. They require human approval.

### Static hosting

- GitHub Pages has no server-side database, authentication, scheduled runtime, or write API.
- Voting, manager submissions, and commissioner editing cannot be implemented as an authoritative in-browser database without an external service.
- GitHub Actions is suitable for scheduled generation, but schedules can be delayed, disabled after repository inactivity, or fail because of provider/API changes.
- Only GitHub Pages-supported Jekyll features and plugins may be used. Avoid custom server plugins.

### Content migration

- Many historical pages are screenshots or graphical recaps. OCR can assist, but scores, names, records, and brackets require manual verification.
- Google Sites asset delivery URLs are not stable source-control assets.
- Embedded media and fight songs may have copyright or hotlinking restrictions.
- Team names and identities have changed across seasons. Stable IDs and alias history are mandatory.
- Some legacy copy contains personal or sensitive information and should not be republished automatically.

### Front-end behavior

- Wide standings/draft tables need responsive patterns that remain readable and accessible.
- Brackets are difficult to render on small screens; structured round cards should supplement or replace oversized images.
- The animated ticker must respect reduced-motion preferences and remain keyboard/screen-reader usable.
- All asset paths must continue to use `relative_url` because the site is hosted under `/fantasy-football-site`.

## Decision summary

The current repository is a viable GitHub Pages/Jekyll foundation, and its hosting model should be retained. The overhaul should not be a collection of copied Google Site pages. It should be a data-driven Jekyll portal built around stable owner/franchise IDs, season-specific Yahoo mappings, curated historical YAML, narrative collections, reusable includes, locally managed assets, and sanitized generated current-season JSON.

The immediate priority is not a visual redesign. It is to establish a synchronized repository baseline, repair and test the Yahoo normalization pipeline, stop exposing unnecessary raw metadata, and scaffold the canonical data model. That is the exact scope recommended for Milestone 2.
